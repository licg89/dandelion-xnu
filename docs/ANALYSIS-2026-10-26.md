# 项目分析：bsd_init 之后的死锁到底在哪

记录时间：2026-10-26（本次分析）
设备：Xiaomi Redmi 9A（dandelion / MT6762G）
内核：xnu-8796.141.3 + `patches/xnu/*.patch`（本次改动后 28 个补丁）
证据来源：源码、issue #1 的现场日志、CI 产物（run#91，commit `1137e5f`）在本地 QEMU 的复现

---

## 0. 结论摘要

| issue #1 的结论 | 复核结果 |
|---|---|
| `configure()` 没卡住，`topLevel == 0` | ✅ 正确 |
| ADT 缺 `top-level` 属性 → 一个设备节点都没有 | ⚠️ 现象正确，**但不是当前阻塞点**（见 §3.2） |
| GIC 不是可用的 GICv3 模式，本机是 GICv2 | ❌ **错误**，结论来自一次读错偏移的探测（见 §3.3） |

本次真正定位到的死因（已用 QEMU 复现并修复）：

1. **GICD_PIDR2 读错偏移**：GICv3 的 distributor 帧是 64 KiB，`PIDR2` 在 `0xFFE8`；
   旧代码读 `0xFE8`（GICv2 的 4 KiB 布局），在真机和 QEMU 上都返回 `0`，
   于是内核判定「arch rev 0，不是 GICv3」并**主动跳过了整个 CPU 接口初始化**。
2. **即使不跳过，原来的初始化也不足以收到中断**：
   `GICD_CTLR` 只写了 `EnableGrp0`，缺少 `ARE_NS` / `EnableGrp1A`；
   redistributor 的组寄存器、PPI 的优先级/触发方式都没配。
   在 QEMU 上复现：只按原序列配置时，`ICC_IAR1_EL1` 永远返回 spurious；
   补上 `EnableGrp1A` 后立刻就能收到 PPI 27。
3. **真机的组模型决定「定时器只能走 IRQ，不能走 FIQ」**：
   真机 `GICD_TYPER = 0x790414`，bit10（SecurityExtn）= 1 → GIC 实现了两个安全态，
   Group0 属于 EL3，非安全 EL1 **不可能**收到 Group0/FIQ。
   而 XNU 的 arm64 定时器路径（`sleh_fiq` → `rtclock_intr`）正是按 Group0/FIQ 写的。
   这不是调参问题，是架构错配。

## 1. 项目是什么 / 边界在哪

在 Redmi 9A 上启动 Apple 开源 XNU 8796.141.3：

```
eMMC → preloader → LK → boot.img（gzip(shim) + pad + DTB）
     → shim（EL2）：FDT 解析 → ADT 合成 → boot_args → EL2→EL1 → 跳 XNU
     → XNU：start.s → arm_init → arm_vm_init → machine_startup → bsd_init
```

四层代码，只有前两层能在本地（Windows + WSL）编译验证：

| 层 | 位置 | 构建 | 本地可验证 |
|---|---|---|---|
| boot shim | `bootshim/` | `bash build.sh <mode>`（clang，WSL 可用） | ✅ 构建 + QEMU 运行 |
| 板级头 + 共享 GIC 代码 | `pexpert/pexpert/arm64/` | 随 shim 一起编译 | ✅ |
| XNU 补丁 | `patches/xnu/*.patch`（28 个） | GitHub Actions `macos-14` | ⚠️ 只能 `git apply` 演练 |
| 平台专家 overlay | `iokit/Kernel/arm/DandelionPlatformExpert.cpp` | 随 shim 的 payload 编译 | ✅ 编译，真机未接线 |

**硬上限（不变）**：开源 XNU 没有 HFS+/APFS，也没有 ext4/f2fs，没有 `md`。
所以即使中断全部打通，内核最终仍停在 `waiting for root device`（`docs/BOOT_STATUS.md` 已经写明）。
本次工作不是让手机上跑起 Android，而是让内核**拥有时间基准、能继续执行**，
从而把「停在哪」从「不可观测的死锁」变成「可观测的稳态」。

## 2. 本地复现环境（本次新增）

`docs/BOOT_STATUS.md` 引用的 `qemu_check.py` / `fbdump.py` / `fbcrop.py` **不在仓库里**，
所以之前的 QEMU 结论无法复现。本次补齐了一个最小可用的 harness：

```bash
# 1) 构建 QEMU 版 shim（控制台走 PL011）
bash bootshim/build.sh xnu-qemu

# 2) 打一个 XNU payload（需要 CI 的 mach_kernel）
python3 bootshim/mkxnu.py mach_kernel -o /tmp/xnu-payload.bin

# 3) 跑，并把 XNU 的 trace ring（0x5fc00000）dump 出来
python3 tools/qemu/qemu_run.py --gic 3 --seconds 30 --initrd /tmp/xnu-payload.bin
python3 tools/qemu/qemu_run.py --gic 2 --seconds 10    # GIC-400 模型
```

要点：

- shim 在 `-DQEMU_VIRT` 下把 framebuffer 控制台镜像到 PL011（`bootshim/fb.c`），
  所以 `-serial file:` 里就是屏幕内容；
- XNU 的 `kprintf` 全部落在 `0x5fc00000` 的 trace ring 里（`osfmk/kern/printf.c`），
  harness 用 QEMU monitor 的 `pmemsave` 把它抓出来，**不需要解码 framebuffer**；
- 两个 GIC 模型（`gic-version=3` → GIC-500，`gic-version=2` → GIC-400）都能跑同一份代码。

没有 macOS 也能做回归：只要有一个 `mach_kernel`（CI 产物 14 天有效）。

## 3. issue #1 逐条复核

### 3.1 结论 1：`configure()` 没有卡住 —— 正确

`topLevel == 0`，`while` 不执行，`configure()` 立即返回。真正停点在它返回之后。

### 3.2 结论 2：ADT 没有 `top-level` —— 现象对，定位不准

`IOPlatformExpert::configure()` 确实靠 `getProperty("top-level")`（一个 `OSSet`）建 nub。
但把它当成「当前阻塞点」有两处偏差：

1. **这个属性不可能来自 ADT**。`top-level` 是 `OSSet`（对象集合），
   而 ADT 的属性只能是字节串；Apple 平台上它是**平台 kext 的 `IOKitPersonalities`**
   里写死的，随 kext 一起加载。本项目**一个 kext 都没有**（`can't perform kext scan: no kext summary`），
   所以无论是 ADT 加属性还是硬编码，都换不来任何驱动匹配。
2. **即使有 nub 也不会 start**：没有 kext 就没有 personality 可匹配；
   IOKit 里只多出几个 `IOPlatformDevice` 条目。
   它对「能不能继续跑」没有影响 —— 证据是 QEMU 里 `topLevel=0` 同样成立，
   而内核照样走到 `waiting for root device`。

结论：这是一条**真实但不紧急**的缺口。本次没有改 ADT 的 `top-level`
（ADT 里写不了 OSSet），而是把它降级为「将来接入 kext 时再做」的待办，
并在文档里写清真正的机制（`IODTPlatformExpert::processTopLevel()` 走的是 DT plane，
和 `top-level` 是两条不同的实现路径）。

### 3.3 结论 3：GIC 不是 GICv3 —— 错，而且错因可复现

issue 的判据是「`GICD_PIDR2` @ `0xc000fe8` = 0」。这个偏移只对 **4 KiB 的 GICv2 distributor 帧**成立。
GICv3（GIC-500/600）的 distributor 帧是 **64 KiB**，外设 ID 寄存器在帧尾：`PIDR2` 在 `0xFFE8`。

QEMU 上同一段代码给出了完全一样的数字（`tools/qemu/qemu_run.py --gic 3`）：

```
  GICD_CTLR  0x50
  GICD_TYPER 0x37a0008
  GICD_IIDR  0x43b
  PIDR2 FE8  0x0          <- 旧代码读这里，得出「arch 0」
  PIDR2 FFE8 0x3b         <- 真正的 GICv3 ID（ArchRev = 3）
  arch rev   3
```

`arch rev 0` 于是触发旧代码的
`if (gic_arch < 3) { kprintf("not GICv3, skipping ICC_* setup"); return; }`
——**内核自己把中断关掉了**，屏幕上当然也不会有异常，只是永远没有 tick。

第二份独立证据来自 shim 自己：`bootshim/shim.c` 在 EL2 里读 `ICC_SRE_EL2`
（`show_cpu_info()`）。这个寄存器在 GICv2 上**不存在**，访问会 UNDEF。
本地用 `--gic 2` 实测：

```
--- CPU ---
CurrentEL   0x0000000000000008
...
EXCEPTION!
Vector= 4
ESR_EL2= 0x00000002000000        <- EC=0x00, ISS=0 => UNDEFINED
```

而真机能打印 `EL1 transition OK` 并一路跑到 `bsd_init`，
说明真机那次 `mrs icc_sre_el2` 是成功的 → **真机确实有 GICv3 系统寄存器接口**
→ 「本机其实是 GICv2」的推断与观测自相矛盾。

（顺带修掉了一个真实隐患：GICv2 设备上 shim 会在 `show_cpu_info` 和 `enter_el1` 里
各崩一次。本次把这两处都改成按设备树 compatible 判断，见 §4。）

### 3.4 真正的死因（新增，已复现）

拆成三件事，按「谁先挡住」排序：

**(a) 内核跳过了 GIC 初始化** —— §3.3，`PIDR2` 偏移错误。

**(b) 初始化不完整** —— 即使 arch rev 判对，旧序列也收不到中断：

- `GICD_CTLR` 只写了 `EnableGrp0`。GICv3 需要 `ARE_NS`（affinity routing）；
  QEMU/hardware 实测还要求 `EnableGrp1A`（bit1），否则 CPU 接口永远 spurious。
- redistributor 侧：旧代码只写了 `IGROUPR0` + `ISENABLER0`，
  没写 PPI 的优先级、`ICFGR`（触发电平）、也没唤醒 redistributor 的组配置。
- CPU 接口：`ICC_PMR_EL1 = 0xFF` 写了，但 `ICC_CTLR_EL1` 直接写 0（含 `EOImode`/`CBPR`），
  `ICC_BPR*` 只写了 BPR0。

QEMU 实测对照（同一份代码，只改 `GICD_CTLR` 一位）：

| `GICD_CTLR` | forced-pending → `ICC_IAR1_EL1` | 定时器 PPI 27 |
|---|---|---|
| `0x51`（ARE + EnableGrp1） | 1020（spurious） | 收不到 |
| `0x53`（+ EnableGrp1A） | **27** | **收到**（`timer -> IRQ (gp1) PENDING`） |

**(c) 组模型错配（真机关键）**

真机 `GICD_TYPER = 0x790414` → bit10（SecurityExtn）= 1 → **两安全态**：

- Group0 归 EL3（secure），非安全 EL1 不可见；
- `ICC_IGRPEN0_EL1`、`ICC_IAR0_EL1` 这类 Group0 寄存器在 EL1 要么被忽略、要么 UNDEF；
- 于是 XNU 的 FIQ 定时器路径（`sleh_fiq` → `rtclock_intr`）**在真机上不可能触发**。

这就是「没有 tick → 任何带超时的阻塞等待都不返回 → `configure: done` 之后一条打印都没有」的完整解释。
QEMU 默认是**单安全态**（`GICD_TYPER` bit10 = 0，`--gic 3` 日志里 `SecurityExtn 0`），
所以 Group0/FIQ 在 QEMU 里能工作 —— 这正好解释了「QEMU 能走、真机走不动」的差异。

## 4. 本次改动

### 4.1 新增共享 GIC 核心 `pexpert/pexpert/arm64/dandelion_gic.h`

一份 freestanding（无 libc / 无内核头）实现，**shim 和 XNU 编译同一份代码**，
所以 QEMU 上验证过的行为就是内核会执行的行为：

| 能力 | 说明 |
|---|---|
| 识别 | 同时读 `PIDR2@0xFE8` 与 `@0xFFE8`，按设备树 compatible 决定哪些偏移安全可读；输出 `arch_rev`、`SecurityExtn`、`IIDR` |
| 模式 | `DGIC_MODE_V2` / `DGIC_MODE_V3` / unknown；GICv2 自动找 GICC（DTB 第二段 / +0x2000 / +0x10000，用 `GICC_IIDR` 确认） |
| 组选择 | 两安全态 → Group1/IRQ；单安全态 → Group0/FIQ；GICv2 一律 Group1（非安全视图 bit0） |
| 初始化 | `GICD_CTLR` 置 `ARE_NS` + `EnableGrp1` + `EnableGrp1A`；全中断分组/优先级/ICFGR/IROUTER；redistributor 唤醒 + SGI/PPI 帧 |
| CPU 接口 | `ICC_SRE_EL1`、`ICC_PMR`、`ICC_BPR0/1`、`ICC_CTLR`、`ICC_IGRPEN0/1`（GICv2 走 GICC MMIO） |
| ack/eoi | 按组选 `IAR0/EOIR0`、`IAR1/EOIR1`，GICv2 走 `GICC_IAR/EOIR` |
| 自检 | 自 SGI + 虚拟定时器「真的会来中断吗」测试（判据是**读 IAR 拿到 INTID**，不是读 pending 位） |

### 4.2 shim：把中断控制器现状打到屏幕上

`bootshim/gic_probe.c` 在 `shim_el1`（跳 XNU 之前）输出：

```

  source  device DTB
  dt gic  arm,gic-v3
  gicd      0x8000000        gicd size 0x10000
  region1   0x80a0000        region1sz 0xf60000
  GICD_CTLR  0x50            GICD_TYPER 0x37a0008   (irq lines 288)
  GICD_IIDR  0x43b
  PIDR2 FE8  0x0             PIDR2 FFE8 0x3b
  arch rev   3
  SecurityExtn 0  single state -> Group0/FIQ usable
  mode     GICv3  group0 (FIQ)
  frame 0x80a0000 typer 0x1000011 waker 0x6  (asleep)
  self redist 0x80a0000
  cpu init ok
  ICC_SRE_EL1 0x7  ICC_IIDR 0x3ff  ICC_CTLR 0x8c00
  GICD_CTLR post 0x53   GICR_WAKER 0x0   IGROUPR0 0xffffffff
    enabled yes  pending no  active no  hpppr 1020 forced-ack 27 ...
```

这段输出**只需要刷 boot.img，不需要重编内核**，是当前最快的取证手段。
判据说明：

- `PIDR2 FFE8` 非 0、`arch rev 3` → 确认 GICv3，旧结论被推翻；
- `SecurityExtn 1` → 真机两安全态，定时器只能走 IRQ；
- `timer -> IRQ (gp1)` 这一行是**决定性**的：它证明「中断能不能到这个 CPU」。

### 4.3 shim 的两个健壮性修复

| 位置 | 问题 | 修复 |
|---|---|---|
| `show_cpu_info()` | 无条件 `mrs icc_sre_el2`，GICv2 上 UNDEF（本地已复现崩溃） | 按设备树 compatible 判断，非 gic-v3 就跳过并打印原因 |
| `enter_el1` (start.S) | 无条件 `msr icc_sre_el2`，同上 | 增加第二个参数 `gic_v3`，为 0 时不写 |
| `fdt.c` | 只认 `arm,gic-v3`，GICv2 节点（`arm,gic-400` / `arm,cortex-a15-gic` …）探测不到 | 补上 v2 compatible 列表 |
| `fb.c` | `QEMU_VIRT` 下 `fb_newline()` 不发换行，串口日志挤成一行 | 补 `\n` |

### 4.4 XNU：`pe_fiq.c` 重写 + `sleh.c` 双路径

`patches/xnu/dandelion-gic-mode.patch`（新，343 行）：

- `pe_init_fiq()` 改为调用共享 core：识别 → 判断模式/组 → 初始化 → 使能 PPI 27；
- 主 CPU 做全量初始化，从核只做自己的 redistributor + CPU 接口（保留 Apple 的结构）；
- 打印 `gic v3 ... secext=1 arch=3 …` / `gic ready: GICv3, timer INTID 27, Group1/IRQ`，
  让屏幕直接给出结论；
- 导出 `dandelion_gic_ack()` / `dandelion_gic_eoi()` / `dandelion_gic_uses_group0()`。

`patches/xnu/non-apple-gicv3-fiq-eoi.patch`（改名含义但保留文件名，61 行）：

- `sleh_fiq`：DANDELION 走 `dandelion_gic_ack/eoi`（按组自动选 IAR0/EOIR0 或 IAR1/EOIR1）；
- `sleh_irq`：**新增** DANDELION 分支 —— 没有中断 kext，所以自己 ack，
  INTID 27 → `rtclock_intr(TRUE)`，其它 INTID 交给（可能为空的）注册 handler，最后 EOI。

这是「两安全态 GIC + 无 kext」这个组合下最小可行的定时器路径。

### 5.1 为什么 QEMU 里读不到内核日志

**更正**：早先记录的「trace ring 被 VM 复用所以读不到」是猜测，不是实测结论。
实测结果是 **QEMU 的 `pmemsave` 命令在这台机器上根本没执行成功**：

```
(qemu) pmemsave 0x5fc00000 0x40000 /tmp/x.bin
invalid char 't' in expression          <- 第三个参数被当成表达式解析
Try "help pmemsave" for more information
```

`help pmemsave` 打印的语法看着是 `pmemsave addr size file`，但无论用十进制/十六进制地址、
无论经 HMP 还是 QMP `human-monitor-command`、无论文件名长短，第三个参数都被当表达式解析
（错误字符总是文件名的第一个字母），所以**一个字节都没 dump 出来**。
`tools/qemu/qemu_run.py` 里的 `pmemsave` 调用因此也拿不到数据，`--fb` 解码同理。

结论：**QEMU 里目前没有可用的内核日志通道**，所以：

- `trace ring` 和 `framebuffer` 两条路都还没有被验证过；
- 「新内核是否比旧内核走得更远」在 QEMU 里**尚无定论**：
  两者 `info registers` 的 PC 相同（都在空闲上下文里），既不能证明是
  `waiting for root device` 的稳态，也不能证明是别的原因。

**下一步（已确定做法，未实现）**：不要再依赖内存 dump，让内核在 QEMU 模式下
直接写 PL011。shim 已经这么做了（`bootshim/fb.c` 的 `QEMU_VIRT` 分支），
内核侧只要在 `osfmk/kern/printf.c` 的 `dandelion_console_putc()` 里加一个
受 boot-arg 控制的 PL011 镜像（例如 `mkxnu.py --cmdline "... qemu=1"`），
`-serial file:` 就能直接拿到 `kprintf` 全文。这是最省事、也最可靠的 QEMU 观察手段。

## 6. 下一步（按优先级）

1. **刷 shim 取 `GIC INVENTORY`**（不需要新内核）。
   期望：`arch rev 3`、`SecurityExtn 1`、`timer -> IRQ (gp1) PENDING`。
   - 若 `SecurityExtn 1` 且 IRQ 通过 → 编译并刷包含本次补丁的内核，看是否越过
     `platform expert: configure`（有 tick 之后，`bsd_init` 应该能继续跑）。
   - 若 `timer -> IRQ` 收不到但 `sgi self-test delivered` → 定时器/PPI 路由问题（检查 `CNTVOFF`、`CNTHCTL`）。
   - 若两者都收不到 → GIC 寄存器映射/时钟被关（MTK 平台需要确认 GIC 是否在某个 infra 时钟域）。
2. **CI 编译验证**：推送后 dispatch `machine=dandelion`，确认新补丁能在 macOS 上编过。
3. **ADT 与 IORegistry**：等真有 kext 再补 `top-level`；现在写了也没有驱动会匹配。
4. **从核启动（PSCI）**：`cpus=1` 之外的 SMP 仍需要 PSCI CPU_ON，与本次改动无关。

## 7. 未验证 / 已知风险（诚实清单）

- **XNU 侧只验证到「能编译」**：GitHub Actions run#94（`machine=dandelion`）通过，
  说明 `pe_fiq.c` / `sleh.c` 的改动语法与类型都对；但真机行为未验证，
  尤其 `sleh_irq` 里从 IRQ 路径调用 `rtclock_intr(TRUE)` 这一步。
- **QEMU 里读不到内核日志**：见 §5.1。`pmemsave` 在这台机器上拒收文件名参数，
  trace ring / framebuffer 两条路都没跑通；内核侧 PL011 镜像尚未实现。
  所以「新内核是否走得更远」在 QEMU 里没有结论，真机 + shim 的 `GIC INVENTORY`
  仍是当前最可靠的判据。
- **GICv2 中断投递未打通**：QEMU 的 GIC-400 模型下 `GICC_IAR` 返回 1022
  （「Group1 但非安全不可见」），即使 `GICD_CTLR=0x1`、`IGROUPR0=0xffffffff`、`GICC_CTLR=0x1`。
  识别与寄存器编程已验证，投递路径未验证。**真机大概率是 GICv3，所以这条是防御性代码**。
- **`GICD_TYPER` 位域解读**：真机 `0x790414` 的 bit20-22 在 GIC-500 手册里属保留位，
  与 QEMU 的 `0x37a0008` 不同。本次只依赖 bit10（SecurityExtn）和 ITLinesNumber，
  其余位不做推断；shim 会把原始值打出来，便于后续核对具体 GIC 型号。
- **`rtclock_intr(TRUE)` 从 IRQ 路径调用**：与 `sleh_fiq` 里的用法一致（同样先置
  `cpu_decrementer = -1`），但没有真机验证。
- **framebuffer 重影**：`docs/BOOT_STATUS.md` 记录的字形双写问题仍在（不影响判读）。
