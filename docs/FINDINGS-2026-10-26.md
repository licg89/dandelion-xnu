# 关键发现：bsd_init 之后的两个独立阻塞

记录时间：2026-10-26
对应内核：commit `1137e5f`（带 `configure` 探针 + 延后打印 GIC ID）
设备：Redmi 9A (dandelion / MT6762G)

## 现场

屏幕最后可见输出：

```
bsd_init: calling setconf
DANDELION: platform expert: instantiating power domains
DANDELION: platform expert: power domains up
DANDELION: platform expert: uuid published
DANDELION: platform expert: configure
DANDELION: gic pidr2=0 arch=0 typer=790414 gicr_typer=0
DANDELION: configure: topLevel=0
DANDELION: configure: done
```

之后没有任何输出。

## 结论 1 —— `configure()` 不是卡点

`topLevel == 0`，`while` 循环一次都没进，函数立刻 `return true`。

之前「停在 platform expert: configure」的印象，是因为那一版还没有 `topLevel` / `done`
这两条打印，把「正常返回但没有后续输出」误判成了「卡在 configure 内部」。

真正的停止点在 `IOPlatformExpert::start()` 返回**之后**。

## 结论 2 —— platform expert 没有任何 top-level 设备节点

`getProperty("top-level")` 返回 NULL。

Apple 的 ADT 在根节点上带一个 `top-level` 属性，列出需要实例化的设备节点名；
`IOPlatformExpert::configure()` 靠它逐个 `createNub()` → `attach()` → `registerService()`。

shim 生成的 ADT **没有这个属性**，于是：

- `createNub()` 一次都没调用
- IORegistry 里除根节点外没有任何设备
- 后续所有 IOKit 驱动匹配（中断控制器、定时器、UART、存储……）都不可能出现

这是比「中断没配好」更靠前的阻塞：即使中断全部修好，没有设备节点也不会启动任何驱动。

## 结论 3 —— GIC 不是可用的 GICv3 系统寄存器模式

观测值：

| 寄存器 | 值 | 含义 |
|---|---|---|
| `GICD_TYPER` @0xc000004 | `0x790414` | 可读且非 0，说明 0xc000000 映射有效 |
| `GICD_PIDR2` @0xc000FE8 | `0` | 读不到架构版本（GICv3 应为 `0x3x`） |
| `GICR_TYPER` @0xc100008 | `0` | 0xc100000 处没有有效 redistributor |

更早的证据：`ICC_SRE_EL1` 读回 `1`，shim 也已在 EL2 写入 `ICC_SRE_EL2 = 0xf`，
但 `msr ICC_BPR0_EL1` 在 EL1 仍然触发 UNDEFINED —— 内核落进 `start.s` 的早期异常
向量原地自旋，屏幕上没有任何输出。

这套现象与 **「GICv3 硬件被配置成 GICv2 兼容模式」** 一致（`GICD_CTLR.ARE_NS = 0`，
redistributor 旁路，CPU 接口走内存映射的 GICC 区）。MTK 平台常见这种做法。

加入 `PIDR2.ArchRev < 3 就跳过 ICC 配置` 的提前返回后，内核才得以越过
`pe_init_fiq()` 一路跑到 `bsd_init`。

## 后果 —— 目前没有任何中断源

- 定时器不跳，`mach_absolute_time` 有值但没有 tick
- 任何带超时的阻塞等待永远不会被唤醒
- 调度器时间片无法推进

这解释了 `configure: done` 之后为什么连 `bsd_init` 的下一步打印都没有：
主线程在第一个阻塞等待处停住了。

## 下一步（按优先级）

1. **补上 top-level 设备节点**
   - 在 shim 的 ADT 根节点写入 `top-level` 属性，列出要暴露的设备；或
   - 让 `DandelionPlatformExpert` 手工创建根 nub（不走 `top-level`）
   - 验证方式：`configure` 里能看到 `createNub` / `attach` / `registerService` 打印

2. **确定 GIC 工作模式**
   - 读 `GICD_CTLR`（0x0），检查 `ARE_NS`（bit 4/5）判断是否 v2 兼容模式
   - 在真实 DTB 里找 GICC 区（MT6765 常见 `0xc400000` 附近）
   - 若确认 v2：在 `pexpert/arm/pe_fiq.c` 实现 GICv2 内存映射路径
     （GICC_CTLR / GICC_PMR / GICC_BPR + GICD_ISENABLER 使能定时器 PPI）
     替换当前的 ICC 系统寄存器路径

3. 定时器中断可用后，再观察 `bsd_init` 能否走到 `waiting for root device`

## 硬上限（不变）

开源 XNU 没有 HFS+/APFS，也没有 ext4/f2fs，没有 `md` 设备。
即使上面全部修好，最终仍会停在 `waiting for root device`，
无法进入用户态 / 启动 Android。这是该移植的结构性边界。
