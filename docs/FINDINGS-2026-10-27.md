# 2026-10-27 内核启动推进记录

## 一句话

内核从「`arm_init` 里就死」推进到「`kernel_startup_initialize_upto(LOCKDOWN)` 返回处」，
也就是 `bsd_init()` 之前的**最后一条语句**。全程靠 eMMC 日志取证，不需要拍照。

## 新增的能力：内核 eMMC 日志

见 `docs/EMMC-LOG.md`。摘要：

- shim 负责 MSDC0 的 bring-up / GPT 查找 / 挑空闲区，把 LBA 通过
  `struct dandelion_emmc_handoff`（`DANDELION.h`，PA `0x5FD00000`）交给内核
- 内核在 `arm_init()` 的 `PE_init_printf()` 之后启动通道，逐行写入
  `flashinfo + 2 MiB`
- 开机流程变成：刷 → 跑 → 进 fastboot → 刷回 Android → `adb` 拉
  `flashinfo` → `read_log_block.py --scan` 解码

## 修掉的两个真实 bug

### 1. `ICC_IGRPEN0_EL1` 是非安全态 UNDEFINED

`dgic_cpuif_init()` 在 GICv3 Group1 分支结束后会回读四个寄存器做体检，
其中包括 `ICC_IGRPEN0_EL1`。这颗 SoC 是**两安全态**（`GICD_TYPER.SecurityExtn=1`），
Group 0 属于 EL3，非安全态读该寄存器是 **UNDEFINED**。早期向量没有处理器，
表现就是**内核静默卡死**。

证据（eMMC 日志，逐条打点）：

```
DANDELION: cpu interface init ...
gic: after sre
gic: bpr1
gic: pmr
gic: ctlr
gic: igrpen1
gic: readback          ← 死在这里
```

修复：不再读 `ICC_IGRPEN0_EL1`，直接记 0。修完后内核一口气越过了 `arm_init`。

### 2. 内核侧 MSDC 映射的地址偏移

`start.s` 里给 MSDC0 加的 Device-nGnRnE 块映射是 2 MiB 粒度，
映射的是块基址 `0x11200000`，而 MSDC0 在 `0x11230000`。
内核按「寄存器偏移」去读 `0x41000000`，实际读到了 **USB 控制器**：

```
eMMC log: MSDC version 0x0 cfg 0x2000      ← 0x2000 是 MUSB 的寄存器
eMMC log: MSDC not where it should be
```

修复：`DANDELION_MSDC_VA = 0x41030000`（虚拟地址带上同样的 0x30000 偏移）。

## 当前的死点

内核日志（eMMC）在最后一次运行时结束于：

```
ulock: buckets ready
[step] phase store: before
[step] phase store: after          ← startup_phase = upto; 执行成功
```

而 `kernel_bootstrap()` 里紧接着的 `DL_MARK("lockdown phase returned")`
**没有出现**，`> OSKextRemoveKextBootstrap` 也没有。

结论：内核死在 `kernel_startup_initialize_upto()` 的**函数返回**处，
即 `bsd_init()` 之前的最后一条语句。

已排除：

- 不是 `startup_phase` 所在只读段的问题（store 前后的标记都打出来了）
- 不是 eMMC 通道静音（framebuffer 的 trace 也停在同一点，照片确认过）

未定的假设：

- **栈 / 返回地址被破坏**。依据：加代码后死点会跟着后移，这是典型的栈破坏特征。
  2284 个启动项里可能有一个在本移植上溢出或用了不兼容的 ABI。
- `kernel_bootstrap_log()` 内联后在 `dandelion_trace_mark()` 里出错。

## 下一步实验（按顺序）

1. 在 `kernel_bootstrap()` 里、`kernel_startup_initialize_upto(...)` **之前**放一个
   `DL_MARK`，再在 `kernel_bootstrap_log("OSKextRemoveKextBootstrap")` **之前**
   放一个。用这两个标记区分「返回失败」和「日志函数失败」。
2. 若确认是返回失败：在 `kernel_bootstrap` 入口把一个哨兵写进局部变量，
   调用返回后校验；若哨兵被改 → 栈破坏，再二分启动项（verbose 的
   `startup_debug=1` 能给出完整顺序，但日志会到 270 KB）。
3. 另一个可行的绕法：把 `kernel_startup_initialize_upto(STARTUP_SUB_LOCKDOWN)`
   改成不返回（尾调用进下一步），这样返回地址损坏就不致命 —— 但这只是掩盖。

## 有用的启动参数

| 参数 | 作用 |
|---|---|
| `startup_debug=1` | 每个启动项打印 `phase/rank/func(arg)`（日志会到 270 KB） |
| `-enable_kprintf_spam` | 现有默认，保持 |
| `wdt=-1` | 关内核看门狗（shim 也关了 TOPRGU） |

## 已知的结构上限（不变）

开源 XNU 没有 APFS/HFS+、没有 ext4/f2fs、没有 `md`，也没有存储驱动。
即便上面这条修好，最终会停在 `waiting for root device`，进不了用户态。
本阶段的目标是「把内核启动序列走完」。

## 收尾补充（同日，三轮实验后）

| 实验 | 结果 |
|---|---|
| 跳过 LOCKDOWN 的 9 个启动项 | ❌ 死点**没有移动** → 凶手不在这 9 项里 |
| shim 交接前使能 PPI 27 + 内核 ICC 初始化 | ✅ cpu interface init returned 0 / icc ready (sre=1 pmr=f0 ctlr=400)，但**死点不变** → **与中断无关** |
| startup_phase 只读段假设 | ❌ store 前后的标记都打出来了 → 不是只读段问题 |

**收敛后的结论**：死点在 kernel_startup_initialize_upto() 执行完
startup_phase = upto; 之后的**函数返回**本身。调用者里紧跟的
DL_MARK("lockdown phase returned") 不出现，说明是 epilogue / 
et 出了问题，
而不是函数体内的任何一条语句。

最强假设仍是**栈 / 保存的 LR 被破坏**（证据：往函数里加代码，死点会跟着后移）。
